# Подготовка актов приготовления из Помогатора для iikoServer

## Формат выгрузки
- Источник: Excel с MAIN или локальная загрузка; пользователь выбирает дату.
- Два акта приготовления за дату: Бухара кухня (BK) и Правда кухня (PK).
- Статус обоих документов: `NEW` (без проведения).
- Поле `documentNumber` намеренно **не передаётся**: предполагается, что iikoServer назначит номер при создании. Само поведение автоматической нумерации **ещё необходимо подтвердить на конкретной установленной версии iikoServer**.
- Прямой запрос «следующий номер iiko» и проверка наличия существующих актов **не выполняются**. Выбор `max(documentNumber)+1` исключён, так как может вызвать гонку при параллельных операциях.
- Экспортируемые файлы называются `production-BK.xml` и `production-PK.xml`, номера документов нигде не выдумываются.
- Подготовка ZIP — локальная; настоящая отправка в iiko пока отключена.

## Данные, без которых iiko не сможет принять документ
- Дата, два склада, положительное количество и однозначная номенклатура iiko остаются необходимыми для корректного XML.
- Загружается актуальный справочник iiko с названием и ID/артикулом. Название **до первой скобки** ищем в справочнике iiko как есть; текст состава в скобках не сравниваем.
- Когда точного совпадения нет или оно неоднозначно, администратор вручную выбирает верную номенклатуру iiko и нажимает «Подтвердить и запомнить». Только подтверждённая связь сохраняется.
- Соответствия хранятся **на сервере Supabase**, в `plan_guest_iiko_mappings` по паре `device_id + source_key`. Доступ — только через `plan-bridge-guest`, авторизацию по коду связанного MAIN. В одном связанном MAIN несколько браузеров получают одну таблицу.
- В памяти браузера держится только текущая копия данных. Нет отдельного `localStorage` для сопоставлений и не требуется править исходный Excel.
- Перед применением сохранённого соответствия ID/артикул снова проверяется **в загруженном справочнике iiko**. Если номенклатура исчезла или стала неоднозначной — требуется ручное подтверждение.
- Компоты разных объёмов нельзя свести к одной iiko-позиции.
- Эти проверки относятся к содержимому документов, **не к наличию документов в iiko**.

## Большие пироги: перевод целых пирогов в куски
- Источник количества для актов — столбец `iiko` выбранного дня.
- Для **больших пирогов из раздела «Выпечка»** в акт «Правда кухня» записывается `количество из iiko × 8`. Например, 3 целых пирога → 24 куска.
- Признак большого пирога: наименование начинается со слова `Пирог` и масса изделия от 900 г (в реальном плане были изделия по 1000 г или 1 кг); либо у этого пирога в поле массы/единицы или самом наименовании указан маркер `кус.`.
- `Пирожок` и `Пирог` небольшого веса без маркера `кус.` не пересчитываются.
- Название номенклатуры программа не переименовывает: оно должно совпадать со справочником iiko. Вес для проверки сохраняется, но в таблицах предпросмотра не показывается.
- В акте БК пересчёт пирогов не применяется. В Excel для проверки количества уже указаны **в кусках**; дата/состав актов и отсутствие проведения неизменны.

## Алгоритм сопоставления номенклатуры
1. Выбрать лист по дате. Количества берём из столбца `iiko`. Формируем БК и ПК, включая конверсию больших пирогов ×8.
2. Загружаем XLSX-справочник номенклатуры iiko (наименование + ID и/или артикул).
3. Для строки `Котлета куриная (филе, яйцо, соль)` выделяем `Котлета куриная` и сначала ищем точное совпадение в каталоге.
4. Если точного совпадения нет, ищем **ранее одобренную** пару `название до скобок → iiko ID/артикул` из общего серверного справочника MAIN.
5. Если пара не найдена, устарела или неоднозначна — показываем строку и поиск по доступным наименованиям/артикулам iiko. Подстановка без выбора администратора запрещена.
6. После подтверждения отправляем `iiko_map_save` в сервер, обновляем сопоставление и повторяем проверку актов **без перезагрузки Excel**.
7. Подключённые к тому же MAIN браузеры используют одну таблицу. Ранее утверждённые пары можно удалять через список «Запомненные соответствия».
8. Если таблица на сервере временно недоступна, сохранённые пары не применяем и пакет не готовим молча. Ошибка отображается пользователю.
9. Пока есть несовпадения, скачивание XML пакета блокируется. Отчёт Excel по несовпадениям доступен.
10. Имя блюда в исходном плане остаётся неизменным для просмотра, но в XML передаётся **подтверждённый ID/артикул iiko**.

## Реальное подключение (позже)
Путь iikoServer: `POST /resto/api/documents/import/productionDocument`. XML-корень `document`, поля `status`, `dateIncoming`, `storeFrom`, `storeTo`, `items/item/amount`, `product` или `productArticle`. `documentNumber` отсутствует.

1. Защищённый серверный адаптер должен хранить секреты отдельно от публичного GitHub Pages; в браузере паролей iiko не будет.
2. Сначала отправить один безопасный пробный документ `NEW` в тестовое окружение/с разрешения владельца и убедиться, что номер назначен системой. Если iiko вернёт ошибку отсутствующего номера, включать отправку нельзя до выбора другого алгоритма.
3. Результат iikoServer возвращается в `documentValidationResult`: код HTTP 200 не гарантирует успех; читать `valid`, `errorMessage` и фактический номер `documentNumber`, если сервер его вернул.
4. Пользователь не хочет дополнительных запросов, сверки существования документа и отдельной предварительной проверки наличия документов. Поэтому не делаем preflight lookup и не рассчитываем следующий номер. Это означает, что повторная отправка может создать дубликаты; UI должен ясно показывать результат первой отправки, не делать автоматических повторов при неизвестном результате, не притворяться идемпотентным.

**Тестовый ZIP не отправляет документы в iiko.**
